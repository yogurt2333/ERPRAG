# 轻量经销 ERP + Hermes MVP 设计

状态：访谈共识；第一张工单的 SQLite 采购入库闭环已实现，其余待实现。本文是完整产品与架构边界，不是整套系统运行完成证明。当前证据见 [采购入库说明](PURCHASE-RECEIPT.md)。

## 1. 产品定义

为一个小型快消经销业务提供单企业、1–2 名等权限经营者使用的轻量 ERP。经营者主要通过 Hermes 的微信文字信道操作，Web/PWA 是确定性兜底入口。系统参考 ERPNext 的业务流程，但不复制其源码、数据库或运行时。

核心原则：ERP 拥有业务事实与规则；Hermes 只是自然语言操作把手。模型不可直接计算金额、决定库存或写数据库。

## 2. MVP 业务闭环

### 2.1 商品与往来单位

- 商品、别名、规格、条码（可选）、库存单位、版本化包装换算。
- 待完善商品只强制品名与库存单位，其余信息生成待办。
- 客户、供应商与常用别名；防止模型静默创建重复主体。
- 单币种人民币；只记实际成交金额，不拆增值税与发票。

### 2.2 采购与应付

- 可先记录采购订单，也允许货已到但订单漏录。
- 到货确认产生采购入库和应付。
- 缺少采购订单不阻塞入库，但产生“到货后补录”待办。
- 供应商付款可指定原单；未指定时按最早到期应付生成分配草稿。
- 超额付款成为供应商预付款。

### 2.3 销售与应收

- 客户订单允许缺货并形成待补货数量。
- 实际送达前不扣库存；MVP 没有装车、配送中或车上库存。
- 送达确认产生销售出库和应收，且绝不允许负库存。
- 销售与收款可由一句话生成联合草稿，但内部是独立、关联的账目。
- 未说明收款则保留应收；部分收款保留余额；超额收款成为客户预收款。

### 2.4 库存与效期

- 库存按最小库存单位记账，业务可使用箱、件、瓶、袋等包装单位。
- 移动加权平均成本；所有金额使用整数分或精确十进制/有理数，禁止浮点金额。
- 效期商品在商品档案维护保质期天数；入库批次录最早生产日期。
- 管理到期日是保守提醒值，不宣称每件商品的精确到期日。
- 支持多仓库、调拨、盘点、报损；盘点差异优先补原始业务，无法还原才追加调整。
- 退货优先关联原单；无法确认来源时进入逻辑隔离库存和待办，不先改变财务结果。

### 2.5 毛利与解释

- 毛利 = 销售收入 − 库存账本销售成本，并按销售退货调整。
- 不称净利润，不含税、工资、房租、水电、折旧和财务费用。
- 退货按原销售记录的成本冲回，不按退货时当前平均成本重算。
- 本地确定性工具重放单据和账本；RAG 只检索 ERP 记录与批准、版本化的内部规则。
- 证据完整时输出已确认原因；证据不足时输出“无法解释”和具体调查目标，不输出概率性原因。

### 2.6 待办、提醒与总结

- 待办是 ERP 持久记录，不存放在 Hermes 会话记忆中。
- 即时提醒：漏录前置单据、逾期应收应付、库存不足、临期、异常退货等。
- 每日汇总：当天未处理事项、收付款、送达未收款、临期和库存异常。
- 每周总结：销售、采购、毛利、回款、欠款、损耗、临期与待办趋势。
- 同一事项当天不重复刷屏；允许立即处理、延后或带原因忽略。

## 3. 微信交互契约

```text
微信文字（微信侧可先做语音转文字）
  → Hermes 识别意图并调用查询工具
  → ERP 校验并生成结构化操作草稿
  → Hermes 原样展示关键字段与影响
  → 经营者自然语言修正或回复“确认”
  → ERP 在一个事务中幂等入账
  → 返回单据、库存、往来余额和待办结果
```

- 每个微信私聊同时只有一个当前待确认草稿。
- 用户不必输入草稿编号；后台保留不可见 ID、版本和幂等键。
- 自然语言修改产生新版本，旧版本失效。
- 重复投递“确认”只能返回第一次结果，不重复扣库存或记账。
- 语音识别不在服务器执行，服务器不保存音频。
- Hermes 使用外部模型；只发送当前任务所需的最小上下文。

建议的 Hermes 工具不是通用 CRUD，而是业务意图级接口：

```text
find_product_candidates
create_or_update_operation_draft
confirm_current_draft
cancel_current_draft
query_stock
query_open_receivables
query_open_payables
query_followups
investigate_gross_profit
get_daily_summary
get_weekly_summary
```

工具返回结构化 JSON。模型不得直接传入“最终库存”“最终毛利”或任意数据库字段更新。

## 4. Web/PWA 兜底

Hermes、微信或模型 API 故障时，ERP 仍必须可用。Web/PWA 提供：

- 商品、客户、供应商维护；
- 采购、入库、销售、送达、收付款；
- 库存、批次、临期、盘点、调拨、报损和退货；
- 应收应付与待办；
- 冲销、调整、备份和归档状态。

公网只开放受控业务 API，不开放通用数据库操作。Web 使用 Passkey：固定 HTTPS 域名、无开放注册、至少两个凭证或离线恢复码、服务端会话 Cookie。1–2 名经营者权限相同，但审计区分具体身份；归档、恢复和设备管理要求近期重新认证。

## 5. 轻量运行架构

```text
Internet
  ├─ WeChat → Hermes Gateway ─┐
  └─ Web/PWA → HTTPS/Caddy ───┼→ Lean ERP API → SQLite (WAL)
                               └→ Remote model API

Background scheduler
  ├─ follow-up detection
  ├─ daily/weekly summaries
  ├─ expiry and overdue checks
  └─ backup/archive proposals
```

- 单个 TypeScript/Node ERP 服务；模块化单体，不做微服务。
- SQLite 在本机持久磁盘，WAL 模式；只有 ERP 服务写库。
- Hermes 独立受限进程/容器，只能调用业务 API，不持有数据库权限。
- 禁用 Hermes 浏览器自动化、本地模型和不必要的代码执行工具。
- 外部模型推理；金额、库存、检索接受和事务均在本地确定性执行。
- 反向代理负责 HTTPS、请求大小限制和基础限流。

## 6. 2 核 2GB 约束

2 核 2GB 是验收约束，不是设计阶段即可声称达成的事实。目标配置：

- 不运行 ERPNext、MariaDB、PostgreSQL或本地模型；
- Node ERP 设置明确堆上限并监控事件循环与内存；
- SQLite 控制缓存、WAL 大小和 checkpoint；
- Hermes 关闭浏览器、沙箱编程等非业务工具并设置内存上限；
- Caddy/Nginx 单实例；
- 配置 2–4GB Swap 作为故障缓冲，但不把持续换页视为正常；
- 所有服务设置健康检查、内存上限和失败重启策略。

上线前必须提供：

- 空闲、日常操作、日报/周报和备份时的 RSS 峰值；
- 100 个连续微信草稿/确认循环；
- 并发 Web 查询 + Hermes 操作 + 备份的压力场景；
- 24–72 小时 soak test；
- 无 OOM、无重复入账、无库存/金额不一致；
- 超限时的降级顺序和告警证据。

若实测不通过，应减少非核心 Hermes 能力或升级内存；不能通过删除账本校验换资源。

## 7. 数据完整性

- 草稿可修改或取消；入账记录不可覆盖或物理删除。
- 修错使用关联冲销、退货或调整，并记录操作者、时间、渠道和原因。
- 销售出库、应收和同句收款在同一数据库事务中提交或全部回滚。
- 库存不变量、往来账不变量、幂等性和精确金额是公共写入边界的测试对象。
- 每个业务写入保存输入快照、草稿版本、确认者和结果引用。

## 8. 备份与冷归档

- RPO 不超过 1 小时，RTO 不超过 4 小时。
- 至少每小时把加密备份复制到服务器外；每天完整备份。
- 保留 7 个每日和 8 个每周恢复点；每月校验，每季度真实恢复演练。
- 主库通常保留 24 个月；磁盘 70% 告警，80% 生成归档草稿。
- 只归档完整关闭月份；未结应收应付、有效批次和未决异常不得迁出。
- 异地包上传并校验成功、经营者确认后，才清理主库；实时库保留索引和当前余额。
- 备份是灾难恢复，冷归档是容量管理，两者不能互相替代。

## 9. 上线方式

采用 7 天小范围双线维护：

1. 选择 10–20 个常用商品、2–3 个客户和 2–3 个供应商。
2. 盘点并确认期初库存、成本、应收和应付。
3. 纸本与新 ERP 同时记录。
4. 每天核对库存、采购、销售、收付款、退货、报损和毛利。
5. 差异记录原因，禁止直接改数字对账。
6. 连续 3 天无未解释差异并完成一次恢复演练后，才扩大范围。

## 10. 分期

### Phase 0：账本内核

- SQLite schema、迁移、精确金额、单位换算和库存事务。
- 采购/销售/退货/盘点/调拨/报损、应收应付和收付款。
- 移动加权成本、冲销、幂等、审计与不变量测试。
- CLI/测试夹具证明业务正确性；不接 Hermes。

### Phase 1：可用 MVP

- Web/PWA、Passkey、受控业务 API。
- Hermes 微信文字入口、结构化草稿与确认。
- 待办、即时提醒、每日/每周汇总。
- 效期、毛利调查、RAG 证据约束。
- 备份、恢复、归档和 2GB 压测。
- 7 天双线试运行。

### Phase 2：增强

- 自动补货建议和销量预测，但只生成建议，不自动采购。
- 更完整的简化 App；复用相同 API，不复制业务逻辑。
- 条码扫描、批量导入、更丰富的经营看板。
- 经真实需求验证后再考虑在途配送、多角色或 PostgreSQL。

## 11. 明确不做

- ERPNext 运行时、源码裁剪或数据库复制；
- 多租户、客户自助订货门户和开放注册；
- 会计凭证、税务、发票、净利润；
- 制造、BOM、项目、人力、工资、资产和电商；
- 报价、采购申请和复杂审批流；
- 车上库存和配送中状态；
- 本地大模型和服务端语音识别；
- 证据不足时由模型猜测毛利原因；
- 模型直接写数据库或自行计算金额。

## 12. 仍需在实现阶段验证，而非访谈决定

- Hermes 当前 WeChat 适配器的消息去重、重连、限流和出站计划任务行为；
- 外部模型供应商的数据保留与故障策略；
- 目标 VPS 的真实磁盘性能、内存峰值和备份上传速度；
- Passkey 在目标手机/浏览器与 PWA 模式下的兼容性；
- 对象存储供应商、区域、生命周期策略和恢复费用；
- 实际业务量下 SQLite 锁等待、WAL 增长和归档耗时。

这些项目未经运行证据不得写成“已支持”。
